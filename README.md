## Краткое содержание

### Задача 1 — BPMN

Смоделирован AS-IS процесс выдачи IT-оборудования. 5 дорожек: пользователь, 1-я линия ТП, отдел снабжения, поставщик, логистика. Главная развилка — «есть ли оборудование на складе?»: ветка «да» (сразу к слиянию) и ветка «нет» (закупка у поставщика → приём → слияние). Слияние стоит **до** общих шагов, поэтому логистика и выдача проходят один раз для обеих ветвей.

Дополнительно к ролям на схеме показаны **3 системы** как Data Store Reference (цилиндры под пулом): Система №1 (обращения), Система №2 (заявки на оборудование), Система №3 (склад/каталог). Каждая задача связана пунктирной линией с системой, которую она использует — это сразу подсвечивает интеграции и точки риска (особенно — что закрытие заявки идёт в две разные системы).

Получение пользователем номера и оборудования смоделированы как `intermediateCatchEvent` с маркером сообщения, обмен с поставщиком — `sendTask`/`receiveTask` (симметричная пара через границу организации).

В `task1_bpmn/notes.md` — детальное описание модели, список из 10 вопросов и противоречий к исходному описанию (SLA, дублирование уведомлений, отсутствующие ветки отказа, расхождения между описанием и реальной архитектурой) и 5 предложений для TO-BE.

### Задача 2 — User Story / Use Case

Фича «Публикация товара на маркетплейсе» — описание требований глазами аналитика Личного кабинета продавца.

Решение состоит из четырёх компонентов:

1. **Декомпозиция требований** — 1 верхнеуровневая User Story → 14 атомарных под-историй (по INVEST). Эпик US-02 (заполнение карточки) разбит на 6 под-историй: категория / название / бренд / артикул / атрибуты / описание.
2. **Архитектурная модель** — две сущности: `Card` (карточка товара) и `EditRequest` (заявка на изменение published-карточки). Это позволяет редактировать опубликованный товар **без снятия с витрины** — ключевое продуктовое решение.
3. **Use Cases** — 5 штук: создание (UC-01), снятие с продажи (UC-02), модерация (UC-03), редактирование без модерации цены / остатка / артикула (UC-04), редактирование с модерацией остальных полей через EditRequest (UC-05).
4. **Process flows** — 3 Activity-диаграммы (Mermaid), state diagrams для Card и EditRequest, 16 открытых вопросов заказчику.

**Ключевые продуктовые решения:** pull-модель модерации (модератор работает в дашборде, не получает email на каждую карточку); один активный EditRequest за раз с заменой через `withdrawn` (паттерн «force-push»); многоуровневая стратегия сохранения черновика (автосейв + localStorage + recovery); уведомления продавцу через 3 канала (in-app + email + SMS на критичных причинах).

Подробности — в `task2_user_story/README.md`.
